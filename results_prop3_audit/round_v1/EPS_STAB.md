## 1. Definition implemented (verbatim from the task)

Per dataset `ds` in {sensorscope, uair}, per seed in `seed30001 … seed30020`, per window `r`.
Active clients of window `r` = client-windows with at least one observed unit
(`n_obs > 0`, equivalently `O` true).

```
Design ON                          Design OFF
zeta_T = pi_tar / max(pi_opp_true, pi_min)      zeta_T = 1
zeta_s = pi_tar / pi_opp_true                   zeta_s = 1

a_T = min(a_max, zeta_T / max(p_obs_true, p_min))     a_s = zeta_s / p_obs_true
d_T = min(d_max, 1 / max(q_use_true, q_min))          d_s = 1 / q_use_true

m_T = n_obs * a_T ;  b_T = m_T * d_T                  b_s = n_obs * a_s * d_s
beta_T = b_T / sum_j b_T_j ;  beta_s = b_s / sum_j b_s_j     (Hajek, active j only)
eps_stab(r) = || beta_T(r) - beta_s(r) ||_1
```

## 3. Resolution of `pi_tar` (resolved, not assumed)

**Mode = `"test"`** → `pi_tar(k,s) = Lambda_s^tar · lambda_{k|s}^tar` computed by
`build_pi_target(atomic, station_to_client, split="test")`: uniform atom mass over the
frozen TEST support, marginalised to the sealed `spatial::block::weekday|weekend` stratum,
times the within-stratum client share (which is 1 for SS/U-Air since each stratum belongs
to one station/client).

Evidence chain:

1. The E3 formal `config_snapshot.json` has **no** `pi_target_mode` key (13 keys), while
   the sibling `e3_f1_score_dependent_r1` snapshots do and record `"pi_target_mode": "test"`.
2. `post_review/G1_support_compatible/DECISION.md`/`THEORY_AUDIT.md` (2026-08-30, after the
   2026-08-11 freeze) contrast the proposed `pi^sc` mixture with the **"original Design"**,
   whose failure mode on U-Air is stated as *"`pi^test = 0` ⇒ `zeta = 0` ⇒ `m = 0`"*, and
   state that `pi^sc` "sets U-Air `pi^tar = 0` from 25.5% of risk units to 0%". The plain
   frozen TEST target is therefore the Design numerator of the formal runs.
   `pi_target_mode="support_compatible"` appears only in that post-review repair path.
3. My reconstruction reproduces that 25.5% exactly: **3,260 / 12,800 = 25.47%** of U-Air
   events carry `pi_tar = 0`, and **72 / 288** U-Air client×stratum pairs have zero mass

## 8. Ambiguities / inconsistencies with the code — stated, not silently resolved

**A. Active set.** The task says active = `n_obs > 0` / `O` true. A follow-up instruction
says to use `window_metrics.json :: active_clients` (`A_r`) as authoritative. These are
different sets and give materially different answers (SensorScope: 12,346 O-active
client-windows vs 4,849 in `A_r`; U-Air: 9,760 vs 2,923 — 13,337 of 22,106 O-active
client-windows are `O=1, U=0`). **Both are reported** (§6a, §6b); neither is privileged
here. `A_r` is the set the code actually aggregates over, so §6b is the
implementation-faithful variant; §6a is the literal task definition.

**B. Design is window-gated in the code, not a static switch.** The code applies
`apply_formal_design_zeta(zeta_d, g_r) = zeta_d if Gate_t else 1`, with `Gate_t` from the
coverage certificate (`zeta_tilde`, `design_from_gate`). The task's "Design ON/OFF" treats
Design as a static setting. The numbers above are the static comparison exactly as
specified; they are **not** the per-window gated realised weights. The frozen
`window_metrics.json` does not expose `Gate_t`, so the gated variant is not computable from
these artifacts.

**C. Granularity.** The code computes `zeta` per `(client, stratum)` and `a` per risk-set
unit; the task uses one scalar row per client-window. These agree here because (i) each
E3 event has exactly one stratum and every risk set lies inside it (verified, 28,800/28,800),
and (ii) `p_obs_true_by_unit` is constant within every event (0/28,800 events with more than
one distinct value; the scalar `p_obs_true` is its mean). So `m_T = n_obs · a_T` equals the
code's `Σ_i O_i a_i` exactly. This would not hold for a different generator.

**D. `q_use_true` is a Monte-Carlo estimate** (`M_MC = 2000`, `q_mc_se` is carried in the
CSV). `eps_stab` is computed from the point estimate; no MC uncertainty is propagated.
Median `q_mc_se` effects are not quantified here.

**E. `pi_opp_true` is the frozen joint law**, not the online estimator the code uses for
`Design` when `pi_opp_joint` is absent. For E3 `pi_opp_joint` is always supplied, so
`pi_opp_true` is exactly the denominator the runner used (verified, max Δ = 0.0).

**F. `n_obs` counts observed units**, median 1 among active client-windows (min 1). Windows
with one active client each holding one observation are therefore common.

## 11. Headline

Over the frozen E3 traces the implemented stabilisation is **not** eps-stable: `eps_stab > 0`
in 81.25 % of SensorScope windows and 74.41 % of U-Air windows under the literal
`O`-active definition (10.71 % / 11.13 % once restricted to the runner's realised `A_r`),
with maxima ≈ 1.15–1.16 (a full unit of L1 mass on the simplex). The residual is driven
almost entirely by the `q`/`d` side: the Design-OFF a-side never clips, while
`q_use_true < 1/d_max` holds for 24.22 % / 23.75 % of observed client-windows and the
`q_min` floor is active for 5.22 % / 5.18 %.
